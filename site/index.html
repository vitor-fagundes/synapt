    Como funciona

    A cada 5 s o orquestrador no AP executa as sete etapas abaixo, em sequência. Durante o replay, as etapas executadas no ciclo atual ficam marcadas. As etapas 1 a 4 e a 7 rodam em todo ciclo; a 5 só quando há órfãos e a 6 só quando algum órfão foi marcado para reclusterização. É o que o CSV permite afirmar.

      Método e proveniência

      Desenho experimental

      • Todas as séries rodam com --run=0 de propósito: a aleatoriedade do NS-3 fica fixa, e o que varia entre rodadas é a carga, ou seja, capacidades dos nós e tarefas sorteadas por std::random_device a cada rodada.
      • As 35 rodadas de um grupo são episódios sucessivos de aprendizado, encadeados pelo knowledge.dat (histórico, R_int, Q-table, ε e contadores S1/S2 passam de uma rodada para a seguinte). A rodada 1 de cada grupo começou sem conhecimento.
      • Os cenários (grupos) são execuções independentes entre si: cada grupo sorteou suas próprias cargas. Comparar a rodada k de dois cenários não é comparar a mesma execução.
      • O agregado mostrado é a média ± DP ao longo das 35 rodadas (DP amostral). Não é um intervalo de confiança: as rodadas não são amostras independentes.

      Tempos reais

      O AP inicia em t = 10 s e seus agendamentos são relativos a esse início. Por isso o primeiro ciclo registrado é t = 170 s (145 ciclos, até 890 s), e as ondas configuradas para 300/450/600 s disparam em 310/460/610 s. No cenário aleatório, cada onda dispara no tempo sorteado + 10 s.

      Quando cada métrica é registrada

      QI, SR, pThreat, TII, ARF, ρ, aprendizado médio e Q médios são registrados na etapa 4, antes do processamento dos órfãos do ciclo. Por isso o ciclo da onda mostra a queda (ex.: QI ≈ 0,79) e o seguinte já mostra o efeito das ações. Os contadores de órfãos, ações e S1/S2 são os do próprio ciclo.

      Nós fora de cluster

      Na eleição inicial, cada nó escolhe um líder. Alguns elegem um nó que nunca vira líder: esses nós ficam fora de cluster desde o início, não são órfãos e não passam pelo mecanismo de recuperação. Isso explica SR < 100% mesmo sem falhas. Se o nó eleito for promovido mais tarde a novo líder (recluster), quem o elegeu passa a ser membro do novo cluster.

      Topologia

      A topologia de cada rodada é reconstruída do simulation.log: eleição inicial, líderes, ondas de falha, decisão de cada órfão (estado, ação, sistema e destino) e novos líderes. As posições vêm da grade do contaski.cc e de N; o log só confirma a distância de cada nó ao AP. Uma rodada só tem trace se passar nas verificações: contagens por ciclo iguais às do CSV; round(SR × vivos) = vivos − órfãos − fora de cluster em todos os ciclos; membros e órfãos de cada líder que cai iguais aos registrados na onda; coerência dos reclusters e dos órfãos pendentes. Os membros de clusters formados por recluster não são registrados no log e não são inferidos.

      Parâmetros por grupo

      Diferenças em relação ao README

      Para o que foi executado vale a precedência logs > código atual > README. O README não foi alterado; as diferenças são:

      • Tempos: o README cita primeiro ciclo em 160 s e ondas em 300/450/600 s; os logs mostram 170 s e 310/460/610 s.
      • Calibragem: o README aplica o override de densidade a todo N ≥ 300. Nos logs, ele aparece nas 35 rodadas de 300_with_failures e em nenhuma de 300_no_failures, que foi gerado antes da calibragem. Em N = 300, sem falhas e com falhas usam parâmetros diferentes.
      • A linha “300 nós — com falhas” da tabela de resultados do README (98,9% ± 0,6% / 98,6% ± 1,8%) corresponde ao grupo 300_with_failures_OLD_backup, anterior à calibragem. Este site usa o 300_with_failures atual.
      • Os exemplos de execução do README usam --run=1; as séries publicadas usaram --run=0.
      • Recluster coletivo: o README diz que o órfão de maior Li vira líder. O código (NodeAPApplication.cc, linhas 1180–1194) elege o de mais capacidades, com desempate pelo menor IP.
      • O README não lista o grupo 250_random_failures e descreve outra organização de pastas; aqui cada rodada fica em results-synapt/<grupo>/run_NNN/.

      Evidência do --run=0

        Seus dados

        Para gerar uma execução, compile o NS-3 e rode o cenário a partir da raiz do ns-3-dev. Os arquivos IntuitiveStats.csv, IntuitiveQValues.txt e APStats.txt são gravados no diretório de execução.

        ./ns3 build
python3 ns3 run --no-build "scratch/synapt/contaski --nNodes=200 --run=0 \
  --knowledgePath=/caminho/para/knowledge.dat \
  --multipleFailures=true --multiFailurePercent=30 --failureTimes=300,450,600"

        Para regenerar os dados deste site a partir de results-synapt/ (o guard deixa a pasta sem escrita durante a execução):

        tools/with_results_guard.sh python3 tools/build_site_data.py

        Carregar trace

        Nesta versão o botão aceita um IntuitiveStats.csv avulso (cabeçalho original de 18 colunas, timestamps crescentes, até 20 MiB). O arquivo é lido só no seu navegador e substitui a rodada exibida, apenas com as métricas. O botão aceita só IntuitiveStats.csv; os traces de topologia são gerados por tools/build_site_data.py a partir do simulation.log de cada rodada.
